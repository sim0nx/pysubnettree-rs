# Lookup algorithms

This page compares longest-prefix-match data structures on the sample routing tables. It covers
lookup speed, memory, and build time, measured in Rust without Python overhead. The code is in
`research/lpm-bench`, a separate crate that is not part of the package.

## Candidates

| Structure | Idea |
|---|---|
| **library (as shipped)** | The library's `PrefixTable` after this evaluation: intervals with inline value ids and a per-family index (see [Decision](#decision)). Its memory includes the sorted entries and parents needed for `lookup()`, exact matches and iteration. |
| previous library layout | The layout before this evaluation. Disjoint address intervals point to *entries* (one more indirection to the value), with a top-16-bit index. |
| intervals (no index) | Intervals with the **value id stored inline**, plain binary search. |
| intervals + idx16 / idx20 | Inline values, direct index on the top 16 or 20 bits. |
| intervals idx16+8 (two-level) | As idx16, but crowded buckets (more than 16 intervals) get a second 8-bit level. |
| intervals, adaptive offset | The index uses the bits *after* the leading bits all prefixes share. IPv6 tables share `2000::/4`. Addresses outside that region are two extra buckets, so bucket selection is branch-free. |
| hash table per length | One hash table per prefix length, probed from the longest length down. |
| binary trie | One node per bit, stored in an array without pointers. |
| tree bitmap, stride 4/5/6 | Eatherton et al. 2004, the structure NLnet Labs chose for rotonda-store (evaluated in try-tries-and-trees). Multibit trie with internal and external bitmaps; the longest prefix inside a node is found with a precomputed ancestor mask. |
| poptrie | Asai & Ohara 2015, our prototype. Direct pointing on the top 16 bits, then 6-bit strides with leaf pushing and leaf compression; children and leaves are addressed with `popcount`. |
| poptrie crate | [nicolaskagami/poptrie](https://github.com/nicolaskagami/poptrie) 0.2.1, the third-party crate, used as is. It does not report its memory. |
| DIR-24-8 | Gupta et al. 1998, IPv4 only. A 2^24-entry table plus 256-entry blocks. The speed reference, at the cost of at least 64 MiB. |

Every candidate is checked against a naive reference on randomized, heavily nested prefix sets,
including the edges of the address space (`cargo test --release`). The benchmark also checks
that all candidates return identical results for all probes.

## Method

- Data: routeviews 2016-02-02, 615,842 IPv4 and 28,744 IPv6 prefixes. Values are AS numbers,
  deduplicated to ids.
- Probes: 2 million each.
  - *random*: uniformly random addresses (IPv6: within `2000::/3`). Many of them do not match.
  - *hits*: random addresses inside random table prefixes.
- *tput*: independent lookups. The CPU can overlap their memory accesses.
- *lat*: each probe depends on the previous result, so lookups cannot overlap. This is closer to
  one lookup per Python call.
- Lookup times are the median of 5 runs, build times the median of 3. Memory is the capacity of
  all allocations.
- Every candidate runs in a fresh process. Measured in one process, earlier candidates change
  the memory placement of later ones, which skewed results by up to 2–3×.
- Machine: AMD Ryzen 9 3900X, 64 MiB L3. Rust 1.99, `opt-level=3`, fat LTO.
- Targets: baseline `x86-64`, which is what wheels are built for by default and has no `popcnt`
  instruction, and `x86-64-v2`, which has `popcnt`.

Reproduce (regenerates the tables below in place):

```shell
cd research/lpm-bench
cargo test --release      # correctness of all candidates
cargo run --release -- --update ../../docs/algorithms.md
RUSTFLAGS="-C target-cpu=x86-64-v2" cargo run --release --target-dir target/v2 -- --update ../../docs/algorithms.md
RUSTFLAGS="-C target-cpu=native" cargo run --release --target-dir target/native -- --label native --update ../../docs/algorithms.md
```

## Findings

1. **Storing the value id in the interval is the biggest win.** It is the same structure, but
   adjacent intervals with the same value (usually the same origin AS) merge. For IPv4 that
   leaves 2.5 MB instead of 17.8 MB (7× less) and makes lookups about 2× faster. The current
   layout points intervals at *entries*, which almost never merge, and needs the entry → value
   lookup on every query. Its timings also vary from process to process (IPv4 hits from 23 to
   45 ns throughput), while the inline layout is stable within about 1 ns.
2. **IPv6 needs a different index.** Almost all IPv6 prefixes share the leading bits `0010`
   (`2000::/4`) and cluster in a few `/16`s, so a top-16-bit index leaves buckets of up to 7,381
   intervals. Indexing the 16 bits *after* the common prefix ("adaptive offset"), plus an 8-bit
   second level for crowded buckets, takes IPv6 hits from about 66 to about 36 ns for 1.4 MB.
   Addresses outside the common region are two extra buckets, so selecting a bucket needs no
   unpredictable branch, which cost up to 10 ns in an earlier version. A 12-bit second level
   saves 1–3 ns more but needs 4× the memory.
3. **IPv4 does not benefit from the second level or a wider index.** The 16+8 two-level index
   costs 8.3 MB and is slower. The 20-bit index saves about 1–4 ns for 4 MB more.
4. **Poptrie is the fastest trie,** but it does not beat the interval design here. For IPv4 it
   is about even on latency (30 vs 33 ns hits) with 2.6× the memory. For IPv6 it ties only with
   `popcnt` (37 vs 36 ns) and falls behind without it (50 ns), which is what default wheels get.
5. **The poptrie crate** ([nicolaskagami/poptrie](https://github.com/nicolaskagami/poptrie)
   0.2.1) is 2–3× slower than our Poptrie prototype on this data, even with
   `target-cpu=native`. Its published 175 M lookups/s (5.7 ns) were measured on 100k
   synthetic prefixes with a 100k-address lookup list, which fits in the CPU caches. On a full
   routing table with 2 million random probes, cache misses dominate. The crate also skips direct
   pointing and resolves leaf → entry → value on each lookup; in exchange it supports cheap
   single inserts.
6. **Tree Bitmap** (rotonda-store's structure) is slower on every metric. Its strength is cheap
   incremental updates, which a "load in bulk, then query" library does not need. Without
   `popcnt` it loses another 30–50 %.
7. **DIR-24-8** is the fastest only while it stays in cache. With random addresses, its 72 MB
   table costs about 66–70 ns latency because of TLB and cache misses.
8. **Hash per length and the binary trie** are clearly slower and are not worth pursuing.

## Decision

The library ships one interval implementation with per-family parameters. Numbers for the shipped
code ("library (as shipped)" rows, x86-64-v2), including the sorted entries and parents that
`lookup()`, exact matches and iteration need:

| | index | memory | random ns (tput / lat) | hits ns (tput / lat) |
|---|---|---:|---:|---:|
| IPv4 | top 16 bits | 10.5 MB (previous layout: 13.9 MB) | 8.1 / 19.1 (16.8 / 31.2) | 16.4 / 33.3 (25.2 / 55.7) |
| IPv6 | 16 bits after the common prefix + 8-bit second level | 2.2 MB (1.9 MB) | 7.6 / 10.8 (2.5 / 2.3) | 42.0 / 41.7 (78.6 / 85.1) |

The numbers are about the same on all three targets, because the structure does not depend on
`popcnt`. Random IPv6 addresses are slower than before. Most of them are unrouted space, which
used to be one trivial bucket. Addresses inside routed networks, the common case, are about 2×
faster.

- `get()`, `[]` and `in` use only the intervals.
- `lookup()` (which returns the matched network), `lookup_all()`, exact matches, iteration and
  serialization use the sorted entries and their parents. The matched network is the first entry
  containing the address on the parent chain of the last entry at or before it.
